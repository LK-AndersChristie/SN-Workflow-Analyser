# AI Instructions — Analyzing ServiceNow Workflow Exports

These instructions are for AI agents (Copilot, ChatGPT, Claude, etc.) receiving an exported ServiceNow workflow `.txt` file generated by `Scripts/extract_sn_workflow.js`.

---

## What you are receiving

A **complete export** of a ServiceNow legacy workflow (Workflow Editor / `workflow_ide.do`), in one of three modes:

- **RITM mode** — a full RITM record export (details, variables, activity log, approvals) plus all workflow executions associated with that RITM
- **Context mode** — an executed workflow with definition + execution data (which activities ran, when, their results, faults, scratchpad state, and the triggering record)
- **Definition mode** — a workflow template (activities, transitions, scripts, config) without execution data

The mode is indicated in the header:
- `SERVICENOW RITM + WORKFLOW EXPORT` — RITM mode
- `SERVICENOW WORKFLOW EXECUTION EXPORT` — context mode
- `SERVICENOW WORKFLOW EXPORT` — definition mode

**Sub-workflows** called by "Workflow" activities are extracted recursively (up to 10 levels deep). Each sub-workflow section is marked with `[DEPTH N]` labels and separated by `####` banners.

Contents:

- **RITM record details** *(RITM mode only)* — number, state, stage, approval status, assigned to, opened by, cat item, description
- **RITM variables** *(RITM mode only)* — all catalog variable name/value pairs from the request
- **Activity log / journal** *(RITM mode only)* — all journal entries (work notes, comments, orchestration messages) in chronological order
- **Approval history** *(RITM mode only)* — approver, state, comments, timestamps
- **Workflow contexts** *(RITM mode only)* — list of all `wf_context` records for the RITM, each extracted in full
- **Execution context** *(context/RITM mode)* — overall state (Executing/Finished/Cancelled), start/end times, the triggering record, and scratchpad
- **Workflow metadata** — name, table it runs on (e.g., `sc_req_item`), scope, description
- **Activity index** — numbered list of all nodes sorted by canvas position
- **Transitions** — every connection between nodes, with condition labels (`Always`, `Yes`, `No`, `Success`, `Failure`, `Policy Failure`)
- **Activity details** — for each node: type, sys_id, position, stage, all configuration content, and execution data (if context/RITM mode)

## How to analyze the workflow

### Step 1: Build the flow diagram

Use the TRANSITIONS section to trace the execution path. Start from `[Begin]` and follow transitions to `[End]`.

- **`[Always]`** — unconditional; the activity always flows here
- **`[Yes]` / `[No]`** — conditional branches from `[If]` nodes
- **`[Success]` / `[Failure]`** — outcome branches from orchestration activities
- **`[Policy Failure]`** — a third outcome for some orchestration activities (e.g., password policy violation)

If an activity has **two outbound transitions to the same target** (e.g., both Success and Failure go to the same node), the workflow continues regardless of the outcome — the branching is effectively a no-op.

### Step 2: Understand activity types

| Type | What it does | Config fields to look for |
|------|-------------|--------------------------|
| **Run Script** | Executes server-side JavaScript | `SCRIPT:` |
| **If** | Conditional branch (Yes/No) | `SCRIPT:` (answer = 'yes'/'no') and `ADVANCED:` (0=simple, 1=advanced) |
| **Set Values** | Updates fields on the current record | `SET THESE VALUES:` (encoded query format: `field=value^field2=value2^EQ`) |
| **Timer** | Waits until a date/time | `FIELD:` (which date field), `TIMER BASED ON:` |
| **Wait for condition** | Pauses until a condition is met | `CONDITION:` (encoded query) and/or `CONDITION SCRIPT:` |
| **Create Task** | Creates a child task (e.g., `sc_task`) | `SHORT DESCRIPTION:`, `TASK TYPE:`, `ADVANCED SCRIPT:`, `INSTRUCTIONS:`, `TASK VALUES FROM:` |
| **Begin** | Workflow entry point | No config |
| **End** | Workflow exit point | No config |
| **Log Message** | Writes to system log | `MESSAGE:` |
| **Orchestration activities** (Deprovision, Update AD Object, Reset AD User Password, etc.) | Runs PowerShell/commands via MID server | `INPUT (orchestration):` JSON with parameter mappings |

### Step 3: Understand script patterns

**Run Script activities** have access to:
- `current` — the GlideRecord being processed (e.g., the `sc_req_item`)
- `workflow.scratchpad` — shared state between activities (like a dictionary)
- `data.get(N)` — databus: results from previous activities by **positional index** (fragile!)

**If activities** must set `answer` to `'yes'` or `'no'` (strings, not booleans).

**Set Values** use encoded query format: `state=2^assignment_group=xxx^EQ`

### Step 4: Check for orchestration gaps

Orchestration activities (PowerShell, AD operations) show only their **INPUT JSON** in the export. The actual execution script, post-processing script, outputs, and conditions are stored on the **activity definition** (template), not the activity instance.

When you see an orchestration activity with just `INPUT (orchestration):`, tell the user:
> "This is an orchestration activity. The export shows the input parameters, but the execution script (PowerShell), post-processing script, outputs, and conditions are stored on the activity definition template. If you need to review those, open the activity in the Workflow Editor → click the relevant tab → copy the content."

### Step 5: Common things to look for

**Bugs and risks:**
- `data.get(N)` with hardcoded indices — fragile, breaks if activities are reordered
- Variable name typos (e.g., `gr` vs `grPersonalansvar`)
- Missing null checks on `getRefRecord()` calls
- `current.update()` without `setWorkflow(false)` — can trigger recursive workflows
- Hardcoded sys_ids for catalog items, groups, users
- Same DomainController/server referenced differently across activities (hardcoded IP vs. `gs.getProperty()`)

**Architecture insights:**
- Scratchpad variables passed between activities
- Which activities set `workflow.scratchpad.failure` and how downstream activities react
- Activities that are defined but have zero inbound transitions (orphaned/dead code)
- If nodes where both Yes and No go to the same target (branch is meaningless)

### Step 6: Analyze execution data (context mode only)

When the export includes execution data (context mode or RITM mode):

**Execution context section:**
- **State** tells you if the workflow completed (`Finished`), is still running (`Executing`), was stopped (`Cancelled`), or is paused (`Waiting`)
- **Record** shows which specific record triggered the workflow (e.g., `sc_req_item / RITM0012345`)
- **Scratchpad** shows the final (or current) state of `workflow.scratchpad` — useful for understanding what values were set during execution

**Per-activity execution data:**
- `[HISTORY]` entries are activities that have completed; `[EXECUTING]` entries are still in-flight
- **State** and **Result** show the outcome (e.g., `Finished` / `Success`, `Finished` / `Failure`)
- **Started/Ended** timestamps let you identify slow activities or bottlenecks
- **FAULT** contains error messages if an activity failed — this is the most important field for debugging
- **Output** may contain return values from orchestration activities
- Activities marked `(not reached)` were never executed in this run — useful for understanding which branch the workflow took

**Debugging execution issues:**
- Look for activities with FAULT descriptions to find the failure point
- Compare the execution path (which activities were reached) against the transitions to understand which branches were taken
- Check the scratchpad for unexpected values that may have caused downstream If-nodes to branch differently than expected
- Look for activities that are still `[EXECUTING]` with old timestamps — these may be stuck (e.g., waiting for an approval that never came, or a timer that hasn't fired)

### Step 7: Analyze RITM exports (RITM mode only)

When the export starts with `SERVICENOW RITM + WORKFLOW EXPORT`:

**RITM record section:**
- **State** and **Stage** show where the RITM is in its lifecycle
- **Approval** shows the current approval status
- **Cat item** identifies which catalog item was ordered

**RITM variables:**
- These are the form values submitted by the requester
- Variable names may be internal (`u_fornavn`) or display labels (`Etternavn`) depending on the catalog item configuration
- Some values are sys_ids referencing other records (users, groups, locations)

**Activity log / journal:**
- Entries are chronological — useful for understanding what happened and when
- `[work_notes]` entries are internal notes; `[comments]` are customer-visible
- `[u_orchestration_notes]` and `[u_orchestration_error]` are written by workflow orchestration activities — these are the most important for debugging automation issues

**Multiple workflow contexts:**
- A single RITM may have multiple workflow contexts (e.g., a main workflow plus sub-workflows, or a workflow that was restarted)
- Each context is extracted in full with its own activity index, transitions, and execution history
- Compare execution timestamps across contexts to understand the order of operations

## What to do if the user also provides manual tab exports

For orchestration activities, the user may additionally paste content from the SN Activity Designer tabs:

- **Generell (General)** — activity name, description
- **Inputs** — parameter definitions (Name, Type, Value mapping)
- **Execution Command** — the actual PowerShell/script that runs on the MID server
- **Outputs** — output variable definitions
- **Post Processing** — server-side JS that runs after the MID server returns
- **Conditions** — Success/Failure/Error routing based on output values

When you receive these, map them to the corresponding activity from the workflow export using the activity name.

**Critical mapping to check**: In the Inputs tab, each input has:
- Name (PowerShell variable name)
- Value (SN expression like `${activityInput.userName}`)

If a Value column is empty, that input is **not mapped** and the PowerShell variable will be null at runtime — this is a common source of bugs.

## ServiceNow domain context

- **`sc_req_item`** — Service Catalog Requested Item (RITM)
- **`sc_task`** — Catalog Task (child of RITM)
- **`sc_item_option_mtom`** — M2M table linking RITM to its catalog variable values
- **`sc_item_option`** — Individual catalog variable value records
- **`sys_user`** — User record
- **`sys_user_group`** — Group record
- **`sys_user_grmember`** — Group membership (M2M)
- **`wf_context`** — Workflow execution context (links a workflow version to a specific record run)
- **`wf_history`** — Completed activity execution records
- **`wf_executing`** — Currently in-flight activity execution records
- **`wf_activity`** — Workflow activity node
- **`sys_variable_value`** — Generic EAV storage (where scripts/config live)
- **`sys_journal_field`** — Journal/activity log entries (work notes, comments, etc.)
- **`sysapproval_approver`** — Approval records
- **`workflow.scratchpad`** — Runtime key-value store shared across activities in a workflow execution
- **`data.get(N)`** — Databus: access results from activity at positional index N
- **`current`** — The record the workflow is running on
- **`gs.getProperty('x')`** — System property lookup
- **MID server** — On-premises agent that executes PowerShell/commands against AD, etc.
